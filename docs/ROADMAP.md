# 路线图

核心功能已经完工：多跳链路、一键纳管、幂等下发、抓包验证、后台采样、配置漂移自愈。下面是接下来值得做的事，按「解决的问题有多真实」排序，不按实现难度。

## 已知限制

这些是当前版本确实做不到或做得不够的地方，写在这里免得被当成 bug 反复排查。

**入口端口的外部可达性没有验证。** 抓包验证是从入口机的 `127.0.0.1` 打标记进去的。走环回意味着不经过 nat PREROUTING 链，所以两类问题它抓不到：NAT 机器的映射填错了（外面根本连不到那个端口），以及有 DNAT 规则把这个端口劫走了（外部流量到不了 relay）。**链路会自证健康，而真实客户端连不上。**

**「合计延迟」是各段建连耗时之和，不是端到端实测。** 想直接测端到端行不通——realm 先本地 accept 再异步拨后端，connect 立刻就返回了，测出来是个假的小数字。各段求和是诚实的模型（链路建连本来就是逐跳串行完成的），但它不等于真实往返。

**没有流量统计。** realm 不导出字节计数，面板也就无从统计。

**单账号。** 首个账号创建后 setup 通道关闭，没有第二个用户、没有只读角色。

**IPv6 未验证。** 代码里没有假设 IPv4，但也从没在 v6 链路上跑过。

**忘记密码没有找回入口。** 只能改数据库，见[运维手册](OPERATIONS.md#账号)。

## 接下来

### 1. 从外部验证入口可达性

对应上面第一条限制，也是目前最值得补的洞。

做法：验证时**从另一台节点**去连入口的公网地址和端口，而不是只在入口机上走环回。这一步能同时抓住 NAT 映射填错和端口被 DNAT 劫走两种情况——两者现在都会伪装成「验证通过」。

### 2. 中间跳加密传输

realm 本身支持 `-a/--listen-transport` 与 `-b/--remote-transport`（ws / tls），面板目前没有暴露。

价值：中转段如果被 QoS 或者协议识别，套一层 ws/tls 就能缓解，而且**不用换转发内核**。属于现成能力没用上，实现主要是 UI 和配置生成。

### 3. 链路异常通知

现在链路挂了只能靠人打开页面看。后台采样已经知道每一跳的存活状态，缺的只是把状态跃迁推出去（Telegram / Webhook）。

要注意的是抑制抖动——一次采样失败就报警会变成狼来了，应该连续 N 轮才通知，恢复也要通知。

### 4. 内核升级的分批推进

改 `RealmVersion` 重新部署后，所有链路会在一个巡检周期内被逐条重启。对现在的规模没问题，链路多了就需要能控制节奏——分批、或者手动确认后再推。

### 5. 配置导出 / 导入

节点和链路导出成 JSON，便于灾备和迁移。注意凭据是用主密钥加密的，**导出文件离开主密钥就没有意义**，这一点必须在 UI 上说清楚，否则会给人「我备份过了」的错觉。

### 6. 只读账号

有人要看链路状态但不该有下发权限时才需要。目前是单账号，加这个要先有角色模型。

## 明确不做

**节点 agent。** 一旦节点上有常驻进程回连面板，这就变成另一个 flux 了。当前模型的全部好处——节点零依赖、被接管的机器只多一个 realm、面板挂了不影响转发——都来自「没有 agent」。

**面板里一键升级 realm 内核。** 内核版本应该跟着面板一起发布、一起测过。让运行中的面板随手换掉转发内核，出问题时很难说清当时跑的是哪个组合。

**支持更多转发内核。** realm 在这个场景上没有明显短板（静态单文件、原生 TCP+UDP、按连接解析域名、内存占用极小）。为了「可选」而抽象出内核接口，只会让每个功能都要在 N 个后端上验证一遍。

**变成通用代理面板。** 节点管理、订阅、协议生成都有成熟项目在做。这个项目只做多跳转发这一件事。
