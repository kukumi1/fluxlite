# 架构

## 全景

面板是唯一的控制点，节点上只有 realm 和 systemd/OpenRC 单元，没有 agent、没有回连、没有常驻代理。所有动作都是面板主动经 SSH 发起的。

```
                    ┌──────────────────────────────────────┐
                    │            fluxlited                 │
   浏览器 ──HTTPS──►│  api → service → planner → applier   │──SSH──► 节点
                    │                ↘ verifier            │
                    │                ↘ prober              │
                    │         store (SQLite)   watcher     │
                    └──────────────────────────────────────┘
```

## 模块

| 模块 | 职责 |
|---|---|
| `api` | HTTP 路由、会话校验、限流、内嵌前端 |
| `auth` | 口令校验、可选 TOTP、失败锁定、会话令牌 |
| `service` | 编排层，把下面几个模块拼成 API 暴露的操作 |
| `model` | 领域类型与不变量校验 |
| `store` | SQLite 持久化，追加式迁移 |
| `prober` | 探测节点的 OS / init / 架构 / realm 版本 / UDP 穿透能力 |
| `planner` | 链路定义 → 各跳的 realm 配置与端口分配 |
| `applier` | SSH 下发，hash 比对幂等，从末跳往前建 |
| `verifier` | 逐跳连通性 + 末跳抓包证明投递 |
| `watcher` | 后台巡检与采样 |
| `sshx` | SSH 连接层，连接池、ProxyJump 链、host key 固定 |
| `cryptox` | 凭据封装、口令哈希、随机令牌 |

## 一条链路的生命周期

```
创建 ──► planner.Allocate ──► store          （只落库，不碰机器）
下发 ──► planner.Build ──► applier.Apply      （SSH 写配置 + 重启）
验证 ──► verifier.Verify                      （逐跳探测 + 末跳抓包）
巡检 ──► applier.Apply（幂等）                 （纠正漂移，每 5 分钟）
采样 ──► applier.Status + verifier.Measure     （存活与延迟，每 30 秒）
```

### 端口分配

`planner.Allocate` 从每个节点的端口池起始向上取第一个空闲端口。「空闲」的判定合并三个来源：

1. 面板数据库里其他链路已占用的端口
2. 节点上正在监听的套接字（`ss -tuln`，netstat 兜底）
3. 节点 nat 表里被 DNAT/REDIRECT 劫走的端口（`iptables-save -t nat`）

第 3 项是最容易被忽略的。DNAT 规则在 PREROUTING 就改写了数据包目标，本地套接字永远收不到，而 `ss` 完全看不见这类占用——绑上去的 relay 会正常启动、正常出现在进程列表里、一个字节收不到。

编辑一条已部署的链路时，**这条链路自己持有的监听端口不算占用**，否则它的入口端口会被自己挡住，任何已部署链路都改不了。但 NAT 占用没有这个豁免：面板只部署 relay、从不写规则，所以那种端口绝不可能是自己的。

### 下发顺序

从**最后一跳往前**。中继不会指向一个还不存在的监听端口，入口只在整条链就绪后才对外提供服务。任何一跳失败，它前面的跳全部跳过——把入口拉起来只会对外广告一条死路。

### 幂等

`applier` 比对配置内容的 hash，一致就什么都不做。realm 没有热重载，重写配置意味着重启进程、掐断所有在跑的连接，所以「没变就不碰」不是优化而是正确性要求。

推论：**任何进入配置文件的东西都会成为重启的理由**。链路的显示名因此不写进配置，只写永不变的 slug ——否则改个名字就会断线。

## 几个决策的由来

### 为什么每条链路一个 realm 实例

realm 不支持配置热重载（`--help` 里没有 reload，实测也没有）。如果整机共用一个 realm 进程管所有转发，改任意一条链路都要重启它，等于掐断这台机器上的全部链路。

代价是 systemd 单元变多（`fluxlite-relay@<slug>`）。换来的是改 A 链路绝不影响 B 链路。

### 为什么下发 musl 构建

realm 的 gnu 构建需要 `/lib64/ld-linux-x86-64.so.2`。Alpine 没有它，而**内核找不到解释器时只返回 ENOENT**，shell 把它显示成 `not found`——一个完全正确的 x86-64 可执行文件，报错看起来像架构不对。

musl 构建是静态链接的，Alpine 和 glibc 发行版通吃，功能标志一模一样。所以两个架构都只发 musl 版。

### 为什么验证必须抓包

realm 先在本地 accept，再异步拨后端。所以：

- 后端全挂，客户端仍然连得上
- 一条物理 RTT 50ms 的链路，建连返回只要 4ms

任何基于「连上了」的判断都是假的。唯一可信的证据是在最后一跳抓包，看到特征串确实出现在发往落地的 payload 里。

两个实现细节是硬需求：

- **`tcpdump` 必须加 `-U`**。默认输出到文件是块缓冲的，低流量端口抓包文件恒空，高流量端口靠无关业务流量填满缓冲区而偶然成功——验证结论会取决于背景流量。
- **过滤条件不能带域名**。tcpdump 会自行解析域名，DDNS 目标可能解析到与 realm 实际连接不同的地址。只按端口过滤。

### 为什么状态从数据库读而不是现查

存活检查要对每一跳开一个 SSH 会话。如果状态接口现查，前端就不能轮询它，界面上的运行状态永远停留在打开页面那一刻。

后台采样把结果写进库，状态接口退化成数据库查询，前端可以随便刷。代价是数据有最多一个采样周期的延迟，所以**采样时间也一并记录**，过期的读数会被明确标记而不是当成现状。

### 为什么巡检不以「进程死没死」为前提

早期版本只在发现 relay 挂掉时重新下发。这漏掉了配置漂移：有人登到机器上手改了配置，进程照常运行，那份改动会一直留着直到下次手动下发。

现在巡检对每条启用的链路都跑一次幂等下发，靠 hash 比对保证没漂移的机器一个字节都不碰。

### 为什么升级 realm 要重启

替换磁盘上的二进制不影响已经在跑的进程。旧 relay 继续跑旧代码，而探测执行 `realm --version` 读的是新二进制——面板会显示升级成功，实际一个节点都没生效。所以 `ensureRealm` 会报告二进制是否被替换，被替换就必须重启。

## 数据模型

```
nodes ──┐
        ├── route_hops ──── routes
nodes ──┘
```

- `nodes` 存连接信息、能力探测结果、端口池。凭据 AES-256-GCM 加密。
- `routes` 存链路定义：显示名、slug、落地地址、协议、启停。
- `route_hops` 存每一跳：节点、顺序、分配到的端口，以及采样出的延迟和存活状态。

**显示名与 slug 分离**：显示名随意（中文、符号、emoji），slug 是从显示名派生的 ASCII 标识，用于 systemd 单元名、配置文件名、日志路径。改显示名不动 slug，所以改名不会重建节点上的服务。

**空值有意义**：`udp_capable`、`running`、`latency_ms` 都可以为 NULL，表示「还没测过」。这和 false / 0 是不同的判断，代码里不允许把它们折叠成同一个。

## 迁移

`store.migrations` 是一个只追加的语句列表，`schema_version` 记录已应用到第几条。**已发布的迁移绝对不能改**——`CREATE TABLE IF NOT EXISTS` 在老库上是空操作，改它只影响全新安装，两种库会静默分叉。

`ADD COLUMN` 在执行前会先查列是否存在。SQLite 没有 `ADD COLUMN IF NOT EXISTS`，而从「已折叠该列的建表语句」创建出来的库会同时满足「列已存在」和「版本号说该迁移未跑」，不检查就会每次启动都失败。
